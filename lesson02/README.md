## 1. 指针：值传递 vs 通过指针改原值

### 1.1 Go 只有值传递

函数参数永远是**拷贝一份**再交给被调函数：

| 传入类型 | 拷贝的是什么 | 函数里改拷贝，调用方看得到吗 |
| -------- | ------------ | ---------------------------- |
| `int`    | 整数本身     | 看不到                       |
| `*int`   | 地址（8 字节） | 通过 `*p` 能改到同一块内存 |
| `[]int`  | 切片头（ptr/len/cap） | 改元素看得到；`append` 换底层数组则不一定 |

所以「引用传递」在 Go 里不是语法特性，而是：**把地址拷过去，双方指向同一份数据**。

### 1.2 题目 1：`addTen(p *int)`

```
main 栈:  n = 5          地址 0xA
           │
           └── 把 0xA 拷给 p
函数栈:    p = 0xA
           *p += 10   →  0xA 处变成 15
```

- `&n` 取地址，`*p` 解引用。
- 必须判 `p == nil`，对空指针解引用会 panic。
- 若写成 `func addTen(n int)`，函数里的 `n` 是副本，`main` 里永远还是 5。

### 1.3 题目 2：切片指针 `*[]int`

切片头已经带底层数组指针，**只改元素**时传 `[]int` 就够：

```
slice header:  ptr ──► [1, 2, 3, 4, 5]
               len=5  cap=5
```

题目要求「切片的指针」，所以签名是 `func doubleSlice(s *[]int)`，访问元素写成 `(*s)[i] *= 2`。

什么时候**必须**用 `*[]int`：函数内部 `append` 可能换新底层数组，只有改调用方的 header（ptr/len/cap），外面才能看到扩容后的切片。本题只改元素，两种写法结果相同，用指针是为了满足题意并说清这个区别。

Go **没有指针运算**（不能 `p++` 移到下一个元素）。遍历靠下标或 `range`，这是有意的安全设计。

## 2. Goroutine：`go` 关键字与并发调度

### 2.1 协程不是系统线程

`go f()` 不会立刻新建一条 OS 线程。Go 运行时用 **GMP** 模型：

- **G（Goroutine）**：用户态协程，栈从约 2KB 起，可动态增长。
- **M（Machine）**：真正的 OS 线程。
- **P（Processor）**：逻辑处理器，手里有本地可运行 G 队列。`GOMAXPROCS` 默认等于 CPU 核数。

调度器把大量 G 复用到少量 M 上。G 遇到系统调用、channel、锁阻塞时，P 可以换另一个 G 继续跑。所以「启动两个协程打印奇偶」的代价远低于两个线程。

### 2.2 题目 1：奇偶两个协程

```go
go printOdd()
go printEven()
wg.Wait()
```

要点：

1. `go` 之后两个函数**并发**执行，打印顺序不确定，这是正常现象，不是 bug。
2. `main` 返回会终止整个进程。必须用 `sync.WaitGroup`（或 channel）等子协程结束，否则可能一个数都打不完。
3. `WaitGroup` 用法：先 `Add(n)`，每个协程 `Done()`，主协程 `Wait()`。`Add` 必须在 `go` 之前，否则可能 `Wait` 时计数还是 0。

### 2.3 题目 2：任务调度器

设计：

```
tasks[] ──► 每个 task 一个 goroutine
              │
              ├─ start := time.Now()
              ├─ task.Fn()
              └─ results[i] = 耗时
         WaitGroup 汇合后返回 results
```

实现要点：

- **循环变量捕获**：`for i, t := range tasks { go func() { ... i, t } }` 在旧编译器里会共享同一对 `i,t`。写成 `i, t := i, t` 再启动协程，每个闭包拿到自己的副本。
- **无锁写结果**：预先 `make([]TaskResult, len(tasks))`，协程 `i` 只写 `results[i]`，下标不重叠，不用 Mutex。
- **墙钟时间 vs 串行时间**：三个任务 sleep 80/30/50ms，并发总时间接近 80ms，而不是 160ms。`time.Since` 量的是该任务自己的墙钟时间。

调度器没有做超时、取消、失败重试；作业范围只覆盖「并发启动 + 汇合 + 计时」。

## 3. 面向对象：接口与组合

Go 没有 class、没有继承。面向对象靠 **结构体 + 方法 + 接口 + 组合**。

### 3.1 题目 1：`Shape` 接口

```go
type Shape interface {
    Area() float64
    Perimeter() float64
}
```

- **隐式实现**：`Rectangle`、`Circle` 只要有这两个方法，就自动是 `Shape`，不用写 `implements`。
- **值接收者** `(r Rectangle)`：方法不改字段。值或指针都能当 `Shape` 用。
- 若用指针接收者 `(r *Rectangle)`，只有指针（或可取址的变量）能赋给 `Shape`，字面量 `Rectangle{...}` 会编译失败。
- `printShape(name string, s Shape)` 面向接口：新增 `Triangle` 不用改打印函数。

接口变量内部是 `(动态类型, 动态值)` 一对。调用 `s.Area()` 时，运行时按动态类型找到对应方法。

面积 / 周长公式：

| 类型      | 面积        | 周长           |
| --------- | ----------- | -------------- |
| Rectangle | `w * h`     | `2 * (w + h)`  |
| Circle    | `π * r * r` | `2 * π * r`    |

### 3.2 题目 2：组合，不是继承

```go
type Person struct {
    Name string
    Age  int
}

type Employee struct {
    Person          // 匿名嵌入
    EmployeeID string
}
```

- 嵌入后字段提升：`e.Name` 等价于 `e.Person.Name`。
- 这是 **has-a**（员工「包含」一个人的信息），不是 **is-a**。Go 刻意不提供继承，避免脆弱基类。
- `PrintInfo` 用值接收者即可：只读。若方法要改 `EmployeeID`，应改成 `(e *Employee)`。
- 若 `Person` 也有方法，会被提升到 `Employee`；外层同名方法会**遮蔽**内层，这是组合下的「重写」方式。

## 4. Channel：协程之间的管道

Channel 是类型化的消息队列，遵循 **CSP**（Communicating Sequential Processes）：用通信来共享内存，而不是用共享内存来通信。

### 4.1 无缓冲 vs 有缓冲

|              | `make(chan T)`      | `make(chan T, N)`        |
| ------------ | ------------------- | ------------------------ |
| 内部队列     | 容量 0              | 容量 N                   |
| 发送         | 必须已有接收方等待  | 队列未满即可发送         |
| 接收         | 必须已有发送方等待  | 队列未空即可接收         |
| 典型用途     | 同步、交接、信号    | 削峰、解耦生产消费速度   |

方向约束：`chan<- T` 只能发，`<-chan T` 只能收。函数签名写成单向，编译器能拦住误用。

### 4.2 题目 1：无缓冲通道传 1~10

```
生产者:  for i=1..10 { ch <- i }  close(ch)
消费者:  for n := range ch { 打印 n }
```

- 无缓冲时，`ch <- i` 会卡住，直到消费者执行 `<-ch`，两者在通道上「握手」。
- **谁 close**：只由发送方关。关了之后 `range` 读完剩余值再退出；再关一次会 panic。
- 接收方不要关通道。双向 `chan` 两边都能关，但约定「发送者负责关闭」。
- 若忘记 `close`，消费者的 `range` 会永远阻塞。

### 4.3 题目 2：缓冲通道传 100 个整数

```go
ch := make(chan int, 16)
```

生产者可以连续塞最多 16 个还不被堵住；消费者慢时，缓冲当队列用。缓冲满了，行为退化为「和消费者同步」。

实现上仍要：

1. 生产者发完 `close(ch)`。
2. 消费者 `range` 直到关闭。
3. `WaitGroup` 等两边都结束（生产者关通道后还会打印一句日志，不能只等消费者）。

缓冲大小不影响正确性，只影响阻塞频率。作业里用 16 是为了让「先积压再消费」能发生，而不是 `N=100` 把 100 个数一次性全放进去（那样几乎看不出「满了才阻塞」）。

## 5. 锁机制：互斥锁与原子操作

### 5.1 为什么 `counter++` 不安全

`counter++` 在 CPU 上至少三步：

1. 从内存读到寄存器
2. 寄存器 +1
3. 写回内存

两个协程交错可能都读到 `7`，都写成 `8`，一次递增丢失。10 个协程各加 1000 次，期望 `10000`，无保护时经常更小。

### 5.2 题目 1：`sync.Mutex`

```
Lock() → 读改写 → Unlock()
```

- Mutex 保证**同一时刻只有一个**协程在临界区。
- 必须成对：`Unlock` 用 `defer` 更安全（本题临界区只有一行，直接 `Unlock` 也清楚）。
- 锁粒度：只锁「改 counter」那一下，不要把整个 1000 次循环包进一把锁，否则协程失去并发意义。
- `WaitGroup` 和 Mutex 职责不同：WaitGroup 管「等结束」，Mutex 管「数据安全」。

互斥锁是悲观的：即使没有冲突也要进出内核态/运行时的锁慢路径（无竞争时 Go 的 Mutex 有自旋快路径）。对「单纯 +1」这种极小临界区，原子操作通常更快。

### 5.3 题目 2：`sync/atomic` 无锁计数

```go
atomic.AddInt64(&counter, 1)
```

底层对应 CPU 的原子指令（x86 上类似 `LOCK XADD`）：总线锁定或缓存行锁定，整次读改写对其他核不可见中间态。

对比：

|              | Mutex                         | atomic                      |
| ------------ | ----------------------------- | --------------------------- |
| 适用         | 多条语句组成的临界区          | 单个整数的加减、CAS、Swap   |
| 是否阻塞     | 抢不到锁的协程会等待          | 不进入睡眠，靠 CPU 原子指令 |
| 可组合性     | 可保护任意数据结构            | 很难无锁地改「两个字段同时」 |
| 本题结果     | 一定是 10000                  | 一定是 10000                |

注意：

- 要用 `int32` / `int64` 等 atomic 支持的类型，普通 `int` 在 32 位上宽度不确定，作业里用 `int64`。
- `atomic.AddInt64` 的第一个参数必须是**对齐的**地址（结构体里自己定义的 `int64` 字段由编译器保证对齐）。
- 「无锁」不是「无同步」：原子操作仍然是同步原语，只是不用 Mutex。

## 6. 这五组题串起来的一条线

```
指针     →  搞清「拷贝」和「同一块内存」
协程     →  把活拆开并行跑
通道     →  并行之后怎么安全地传数据（通信）
锁/原子  →  并行之后怎么安全地改同一份数据（共享内存）
接口/组合 →  用类型把上述能力组织成可扩展的程序
```

Go 的推荐顺序是：**能用 channel 表达的同步，优先 channel；共享状态必须改时，再用 Mutex / atomic。**
