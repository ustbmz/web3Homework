# MetaNode 永续合约项目拆解文档

> 学习目标：从**业务**理解项目。读完应能讲清 paper/credit、链下撮合链上结算、资金费、清算，以及 Relayer 为什么必须是 `validOrderSender`。  
> 代码依据：`src/`（合约）、`others/backend/`（撮合引擎）、`others/fe/`（前端）。  
> 仓库：https://github.com/MetaNodeAcademy/perpetual-contract

## 0. 一句话讲清这个项目

MetaNode 是一个 **链下撮合、链上结算** 的去中心化永续合约教学系统。

用户用 EIP-712 签限价单，发给后端 Relayer；Relayer 在内存订单簿里配对后，以 `validOrderSender` 身份调用 `Perpetual.trade`。合约只做三件事：验签、改 paper/credit、检查保证金够不够。资金费率用累计值写在市场合约上，所有持仓的 credit 会自动跟着变，不必逐个改存储。

它不是 NFT 市场，也不是 Pledge 那种固定期限借贷。买卖的是「锚定 BTC/ETH 现货的无限期合约」，用保证金加杠杆，靠资金费把合约价拉回现货。

## 术语说明

下面这些名称在这份合约里有固定用法，不能只按字面理解。表里的「链上」都指这份永续合约里的用法。

| 名称 | 字面 | 在这条链上 |
| --- | --- | --- |
| `paper` | 纸 | 这个市场的仓位张数。正数做多，负数做空。存在 `Perpetual` 的用户槽里 |
| `credit` | 信用 | 这张仓位对应的资金。多头为负，空头为正。不单独存，读的时候算出来 |
| `reducedCredit` | 约减后的信用 | 真正写进 `Perpetual` 的资金。`credit = paper × fundingRate + reducedCredit`。资金费更新时这个数不动 |
| `primaryCredit` | 主信用 | Dealer 里的 USDC 余额，可以为负。存款、平仓盈亏、坏账都改这里。取款按这个数把币转出 |
| `secondaryCredit` | 次级信用 | 第二种保证金的余额。贯穿例子不用它。取走 USDC 时不能靠它来凑初始保证金 |
| `balanceMap` | 余额表 | `Perpetual` 上 `地址 => { paper, reducedCredit }`。没有 `credit` 这一列 |
| `balanceOf` | 余额 | 返回这个市场的 `paper` 和算出来的 `credit`。不是钱包里的币，也不是 `primaryCredit` |
| `paperChange` / `creditChange` | 纸 / 信用的变化 | 这一笔结算的增减量，不是结算后的新余额。`_settle` 拿它们去改旧账 |
| `executeWithdraw` | 执行取款 | 两步取款的第二步。`requestWithdraw` 只记金额和时间锁；时间到了这一步才转出 USDC，取完还必须过 Solid IM |
| `openPosition` | 开仓 | 不写张数。旧 `paper` 从 0 变成非 0 时，把这个市场地址推进 Dealer 的 `openPositions` |
| `openPositions` | 持仓列表 | 这个用户正在哪些 `Perpetual` 上有仓。算净值时按这张表逐个去问 `balanceOf` |
| `realizePnl` | 实现盈亏 | `paper` 变成 0 时，把剩下的 `reducedCredit` 加进 `primaryCredit`，再把这个市场从 `openPositions` 去掉 |
| `fundingRate` | 资金费率 | 市场上的一个累计数。绝对值没意义，两次的差额才是这段资金费。只改这一个数，不改每个用户的槽 |
| `Δ` | delta，变化量 | 这一次资金费的增量。累计值从 `F` 改成 `F+Δ`。正数让多头 `credit` 变大，负数让多头 `credit` 变小。测试里写成 `1e14` 或 `-2e14` |
| `FundingRateKeeper` | 资金费保管人 | 唯一能调用 `updateFundingRate` 的地址。不保管用户的 USDC |
| `Perpetual` | 永久 | 一个市场的合约。BTC-PERP 一份，ETH-PERP 另一份。只记这个市场的 `paper`、`reducedCredit` 和 `fundingRate` |
| `Dealer` / `MetaNodeDealer` | 交易商 | 协议入口合约的名字，不是和你对赌的对手。保管 USDC、验签名、做保证金检查。`Perpetual` 的 owner 就是它 |
| `Relayer` | 中继 | 链下撮合服务用来发 `trade` 的地址。合约字段名是 `orderSender` |
| `validOrderSender` | 有效订单发送者 | Owner 写入的白名单。不在名单里调用 `trade`，第一句就失败 |
| `Maker` / `Taker` | 做市者 / 吃单者 | 挂在簿上等人来吃的是 Maker，主动来吃的是 Taker。成交价用 Maker 的 `credit / paper` |
| `markPrice` | 标记价格 | 预言机价格，用来算净值和清算价。不是刚才那一笔的成交价 |
| `EIP-712` | 提案编号 | 订单签名的格式。链上按类型哈希重算，核对是不是 `signer` 签的 |
| `nonce` | 一次性数字 | 塞在订单 `info` 里，用来区分其他字段相同的两张单 |
| `USDC` | 代币符号 | 本项目的保证金代币，金额按 6 位小数记 |
| `IM` / `Solid IM` | 初始保证金 | 开仓、取款要净值 ≥ 敞口 × `initialMarginRatio`。Solid IM 是取走 USDC 时更严的一档 |
| `liquidationThreshold` | 清算阈值 | 维持保证金率。净值低于敞口 × 这个比例才能被清算。文档里的 MM 就是它 |
| `expectCredit` | 期望资金 | 清算者能接受的最差结果。实际成交差过这条线，整笔清算回滚 |

## 1. 项目解决什么问题

永续合约让交易者不必交割现货，也能做多/做空标的价格，并且没有到期日。要把这件事做成链上协议，必须同时解决：

| 问题 | MetaNode 的做法 |
| --- | --- |
| 订单太多，链上撮合太贵 | 订单在链下签名，Relayer 撮合后再一笔上链 |
| 仓位怎么记账 | 每个市场一个 `Perpetual`：`paper`（张数）+ `credit`（资金） |
| 多市场共用保证金 | `MetaNodeDealer.primaryCredit` 全仓，跨 BTC/ETH 共享 |
| 合约价偏离现货 | 累计 `fundingRate`，多空互相付钱 |
| 保证金不足 | 任何人可 `liquidate`，折扣接手仓位，坏账进保险账户 |

和中心化交易所（Binance 永续）的差别：撮合仍在服务器，但**结算、保证金、清算规则在合约里**，Relayer 不能凭空改你的仓位——必须带上你签过的单。

和 Pledge / NFTMarket 对照：

| | Pledge | NFTMarket | MetaNode 永续 |
| --- | --- | --- | --- |
| 链上核心 | 资金池状态机 | 订单簿 + Vault | Perpetual 资产负债表 + Dealer |
| 订单在哪 | 无订单 | 链上 | **链下签名** |
| 后端角色 | 轮询 view | 扫事件 | **撮合引擎，会发 `trade()`** |
| 钱谁管 | PledgePool | Vault | Dealer 里的 USDC 保证金 |

注意：这里的后端**会发交易**，但发的是「把已签名订单提交结算」，不能替用户动保证金（存款用户自己 `deposit`）。

## 4. 角色、仓位与订单

### 4.1 角色（交易者、Relayer、清算者、FundingRateKeeper、Owner、保险账户）

用户自己只动保证金。开仓、平仓是签好单交给 Relayer，Relayer 再调 `Perpetual.trade`。清算不走订单簿，清算人直接调 `liquidate`。

**交易者**

存 USDC、签名。签名本身不改仓位。

| 动作 | 注解 |
| --- | --- |
| `deposit` | 谁都能调。`transferFrom(msg.sender)` 把 USDC 打进 Dealer，加到 `primaryCredit[to]`。不看仓位，也不需要 Relayer。只存款时 `Perpetual.balanceOf` 仍是 0 |
| `requestWithdraw` | 本人，或已被 `approveFundOperator` 授权够额度的人。只记下待取金额和 `now + withdrawTimeLock`，这时不转币 |
| `executeWithdraw` | 时间锁到了才转出。取的是主资产 USDC 时，取完必须过 Solid IM：净值仍 ≥ 初始保证金，不能把账户抽干 |
| 签名 `Order` | 链下 EIP-712。`paper` 与 `credit` 必须异号。Relayer 不上链，仓位不变 |

**Relayer（orderSender）**

撮合在链下。链上只提交已经配对好的结果。

| 动作 | 注解 |
| --- | --- |
| `Perpetual.trade` | `msg.sender` 必须在 `validOrderSender` 里，否则 `approveTrade` 第一句 `INVALID_ORDER_SENDER`。用户自己调也会失败。验签、未过期、未超量成交之后，对每个人 `_settle`，再要求全部过 `isAllSafe`（维持保证金）。有一人不够，整笔回滚 |
| 手续费 | 从双方 `credit` 里扣，记给 orderSender。成交价用 Maker 的 `credit/paper`，Taker 的价格只做限价保护 |

**清算者**

不签名、不进订单簿。按标记价折扣接手已经不安全的仓。

| 动作 | 注解 |
| --- | --- |
| `Perpetual.liquidate` | 公开函数，不看 `validOrderSender`。调用者必须是清算者本人，或他登记过的操作员。不能清算自己。对方净值必须已经 `<` 维持保证金，否则 `ACCOUNT_IS_SAFE` |
| 成交价 | 合约用标记价算，不吃盘口。接多仓：`标记价 × (1 - liquidationPriceOff)`。接空仓则加同样的偏移。`requestPaper` 可以小于整张仓 |
| `expectCredit` | 清算者能接受的最差结果。实际价差过这条线，`LIQUIDATION_PRICE_PROTECTION`，整笔回滚，两边仓位不动 |
| 接手之后 | 清算者自己必须仍然 `isSafe`。被清算者 `paper` 变成 0 时才 `handleBadDebt` |

**FundingRateKeeper**

| 动作 | 注解 |
| --- | --- |
| `Dealer.updateFundingRate` | 只有 `fundingRateKeeper` 能调。两个数组长度必须相同。它把新的累计值写进每个 Perpetual，不逐个改用户存储。用户的 `credit = paper × fundingRate + reducedCredit`，差额乘在 `paper` 上 |

**Owner**

| 动作 | 注解 |
| --- | --- |
| `setOrderSender` | 把 Relayer 地址写进 `validOrderSender`。没设这个，两张合法签名单也成交不了 |
| `setPerpRiskParams` | 注册或修改市场。`liquidationPriceOff + insuranceFeeRate` 不能大于 `liquidationThreshold`。`isRegistered` 为假的市场不能交易 |
| `setFundingRateKeeper` | 换掉能写资金费的地址 |
| `setInsurance` | 换掉保险账户地址 |
| `setWithdrawTimeLock` | 改取款要等多久。锁的是「链下单还在、钱先被取走」 |

**保险账户**

没有自己的函数。地址由 Owner 的 `setInsurance` 指定，在 Dealer 里有一份 `primaryCredit`。每次清算按 `insuranceFeeRate` 从被清算者的成交额里扣一笔加给它。仓位清到 0 且余额仍是负数时，`handleBadDebt` 把被清算者写成 0，这个负数加进保险账户。

### 4.2 paper / credit（贯穿全项目的账本）

每个市场、每个用户只有两个数：

| | 做多 1 BTC @ 30000 | 做空 1 BTC @ 30000 |
| --- | --- | --- |
| paper | +1e18 | -1e18 |
| credit | -30000e6 | +30000e6 |

读成：「我手里有 +1 张 BTC 纸，同时欠 30000 USDC」或反过来。  
**未实现盈亏不单独存。** 现价来了用：

```
仓位价值 = paper × markPrice + credit
```

BTC 涨到 31000：多头价值 = 1×31000 + (-30000) = +1000；空头 = -1×31000 + 30000 = -1000。这就是永续盈亏。

精度习惯：paper 用 1e18，USDC credit 用 6 位。订单里 `price ≈ |credit| / |paper|`。

### 4.3 订单（链下签、链上验）

```
Order {
  perp, signer,
  paperAmount,   // 正做多，负做空
  creditAmount,  // 必须与 paper 异号
  info           // 打包 makerFee / takerFee / expiration / nonce
}
```

EIP-712 类型哈希在 `Types.ORDER_TYPEHASH`。成交价用 **Maker 价**，Taker 价当限价保护。

## 5. 核心业务流程

![](https://files.seeusercontent.com/2026/11/24/sxZ8/Perpetual.png)

```mermaid
sequenceDiagram
    participant U as 用户
    participant FE as 前端
    participant R as Relayer
    participant P as Perpetual
    participant D as Dealer

    U->>D: deposit(USDC)
    Note over D: transferFrom 打进 Dealer<br/>primaryCredit[to] 增加<br/>不改 paper，balanceOf 仍是 0
    U->>FE: 填数量和限价
    FE->>U: EIP-712 签名
    Note over U,FE: 只签 Order，不上链<br/>paper 与 credit 必须异号<br/>仓位不变
    FE->>R: POST /api/v1/orders
    Note over R: 订单进内存簿<br/>链上还没有这笔成交
    R->>R: 内存簿配对，taker 吃 maker
    Note over R: 成交价用 Maker 的 credit/paper<br/>Taker 的价格只做限价
    R->>P: trade(tradeData)
    Note over P: msg.sender 必须在 validOrderSender<br/>用户自己调会 INVALID_ORDER_SENDER
    P->>D: approveTrade(msg.sender, tradeData)
    Note over D: 解码出订单、签名、成交量<br/>验签、未过期、未超量、禁止自成交<br/>手续费从 credit 扣给 Relayer
    D-->>P: traderList, paperChange, creditChange
    P->>P: 对每个人 _settle
    Note over P: 改 paper 和 reducedCredit<br/>旧 paper 为 0 则 openPosition<br/>新 paper 为 0 则 realizePnl 进保证金
    P->>D: isAllSafe(traderList)
    Note over D: 查的是维持保证金<br/>有一人不够，整笔 revert
```

| 步骤 | 注解 |
| --- | --- |
| `deposit` | 谁都能调。USDC 进 Dealer，只加 `primaryCredit`。Perpetual 的 `paper` / `credit` 不动 |
| EIP-712 签名 | 链下。Relayer 不上链，仓位不变。`paper` 与 `credit` 异号，价格 ≈ `|credit| / |paper|` |
| 内存簿配对 | 不写合约。Taker 吃 Maker，成交 credit 按 Maker 的报价算 |
| `Perpetual.trade` | 入参是打包后的 `tradeData`。`msg.sender` 是 Relayer，必须已在 `validOrderSender` |
| `approveTrade` | 只有已注册的 Perpetual 能调。验签通过后返回三列变化，这时还没改用户仓位 |
| `_settle` | 写入 `paper` 和 `reducedCredit`。新市场通知 Dealer 记入 `openPositions`。`paper` 归零时，剩余盈亏打进 `primaryCredit` |
| `isAllSafe` | 结算之后查每个参与者的净值是否 ≥ 维持保证金。一个人不够，前面的 `_settle` 一起回滚 |

只有三种操作会改 Perpetual 余额：**交易、资金费、清算**。存款只改 Dealer 的 `primaryCredit`。资金费只改市场的累计 `fundingRate`，不逐个写用户槽。清算走 `liquidate`，不经过上面这条 `trade`。

## 6. 合约层

### 6.1 合约如何协作

```mermaid
flowchart LR
    Relayer -->|trade| Perp[Perpetual]
    Perp -->|approveTrade / isAllSafe / realizePnl| Dealer[MetaNodeDealer]
    Dealer --> Trading
    Dealer --> Liquidation
    Dealer --> Funding
    Dealer --> Position
    Dealer --> Oracle
    Owner -->|updateFundingRate| Dealer
    Dealer -->|updateFundingRate| Perp
```

`MetaNodeDealer` 是拼盘入口：

- `MetaNodeStorage`：所有状态
- `MetaNodeExternal`：用户与 Perp 回调
- `MetaNodeOperation`：管理员
- `MetaNodeView`：查询

一个 Dealer 挂多个 Perpetual（BTC-PERP、ETH-PERP）。Perpetual 的 `owner` 就是 Dealer。

| 文件 | 职责 |
| --- | --- |
| `Perpetual.sol` | paper/reducedCredit、trade、liquidate、fundingRate |
| `MetaNodeDealer.sol` | 顶层入口 |
| `libraries/Trading.sol` | 验价、按 Maker 价成交、手续费 |
| `libraries/Liquidation.sol` | 净值/敞口、IM/MM、清算折扣、坏账 |
| `libraries/Funding.sol` | 存取款、时间锁 |
| `libraries/Position.sol` | openPositions 列表、平仓 realizePnl |
| `libraries/EIP712.sol` | 域分隔与订单哈希 |
| `oracle/*` | 标记价格 |
| `subaccount/*` | 独立保证金账户，钱包当 owner |

### 6.2 用户 / Relayer 操作 → 合约方法

| 业务 | 方法 | 谁能调 | 改什么 |
| --- | --- | --- | --- |
| 存保证金 | `Dealer.deposit` | 用户 | `primaryCredit +=`，USDC 转入 Dealer |
| 申请取款 | `requestWithdraw` | 用户/操作员 | 记下 pending + 时间锁 |
| 执行取款 | `executeWithdraw` | 用户 | 取后须 IM 安全 |
| 快速取款 | `fastWithdraw` | 白名单 | 跳过时间锁 |
| 提交成交 | `Perpetual.trade` | 任意人调用，但 **orderSender 须在白名单** | paper/credit |
| 清算 | `Perpetual.liquidate` | 任意人 | 折扣换仓，可能 handleBadDebt |
| 更新资金费 | `Dealer.updateFundingRate` | fundingRateKeeper | Perp.fundingRate 累计值 |

`trade` 的 `msg.sender` 才是 orderSender。普通人调 `trade` 会在 `approveTrade` 里被 `INVALID_ORDER_SENDER` 挡住。

### 6.3 资金费率为什么不改每个用户的存储

```
credit = paper × fundingRate + reducedCredit
```

`fundingRate` 是**累计值**，绝对值没意义，**变化量**才是本期费率。  
Keeper 把累计值从 `F` 改成 `F+Δ`：

- 多头 paper>0：credit 自动 + paper×Δ
- 空头 paper<0：credit 自动 - |paper|×Δ

只写一个 slot，所有持仓的 `credit` 在下次 `balanceOf` 时一起变。用户槽里的 `reducedCredit` 不动。

合约价高于现货时，该惩罚多头，`paper > 0` 的 `credit` 要减少。公式是 `credit 的变化 = paper × Δ`，所以这时 Keeper 写入的 `Δ` 是负数。测试 `ScenarioFundingRateTest` 里 `+1e14` 的断言是多头 `credit` 增加。文件头「正费率 = 多头付费」和断言相反，以公式和断言为准。

### 6.4 成交怎么改账

`Trading._matchOrders`：

1. 至少 1 个 taker + 1 个 maker；maker 按 signer 地址排序
2. taker 成交量 = 所有 maker 成交量之和
3. `_priceMatchCheck`：方向相反，且成交不劣于 taker 限价
4. 成交 credit 按 **Maker 的 credit/paper** 算
5. maker/taker 手续费从 credit 扣，进 `orderSenderFee`（Relayer）
6. 回到 Perpetual `_settle`：更新 paper 与 reducedCredit
7. 新开仓 → `openPosition`；paper 归零 → `realizePnl` 把剩余 credit 打进 `primaryCredit`

### 6.5 风险与清算

全仓口径（`Liquidation.getTotalExposure`）：

```
仓位价值 = Σ (paper × markPrice + credit)
净值     = 仓位价值 + primaryCredit + secondaryCredit
敞口     = Σ |paper × markPrice|
初始保证金 IM = 敞口 × initialMarginRatio
维持保证金 MM = 敞口 × liquidationThreshold
```

- MM 不够：可被清算（`isSafe == false`）
- IM 不够：不能新开仓 / 普通取款
- Solid IM：取主资产时不能靠次级资产撑场面

清算：以 `markPrice × (1 ± liquidationPriceOff)` 折扣把仓位转给清算者，再抽 `insuranceFeeRate` 进保险账户。仓位清零若 `primaryCredit < 0`，保险账户扛坏账。

`expectCredit` 是清算者的滑点保护，执行价差过大会 revert。

### 6.6 保证金进出

存款不经 Relayer。取款两步是为了避免「链下单还在簿上、链上保证金已经被提走、成交时才发现不安全」。时间锁窗口内 Relayer 还能把单成交或撤销。

## 11. 讲解提纲

**1. 这是什么**  
链下撮合、链上结算的永续合约。全仓 USDC 保证金，资金费锚定现货。

**2. 仓位怎么记**  
paper 正负表示多空，credit 是对应的美元账。净值用标记价当场算，不存浮盈字段。

**3. 为什么资金费只改一个变量**  
`credit = paper * fundingRate + reducedCredit`，改累计费率等于给所有人结算。

**4. 谁能成交**  
只有 `validOrderSender` 提交的、带用户 EIP-712 签名的 tradeData。

**5. 后端干什么**  
订单簿 + 把配对结果打成 `trade()`。不能替用户 deposit。

**6. 风险点**  
Relayer 审查/宕机则无法成交（结算仍安全）；资金费 Keeper 不更新则基差不收敛；清算依赖有人来叫 `liquidate`。

## 12. 读完后的自检

1. 做多 1 BTC @ 30000，paper 和 credit 符号是什么？

   `paper` 为正，`credit` 为负。

2. 标记价变了，链上哪个存储字段会立刻变？

   仓位槽不变。净值用 `markPrice` 当场算。

3. 用户为什么几乎从不自己调 `Perpetual.trade`？

   调用者必须在 `validOrderSender` 里，否则 `INVALID_ORDER_SENDER`。用户只签名。

4. 成交价用 Maker 还是 Taker？

   Maker 的 `credit / paper`。

5. 平仓后钱回到哪里（Perp 还是 `primaryCredit`）？

   `primaryCredit`。`paper` 归零时 `realizePnl` 打进 Dealer。

6. 资金费更新有没有 for 循环用户？

   没有。只改市场的 `fundingRate`。

7. MM 不够和 IM 不够分别限制什么？

   MM 不够可被清算。IM 不够不能开仓，也不能普通取款。

8. `requestWithdraw` 为什么要时间锁？

   链下单可能还在簿上。先留时间成交或撤掉，再转走保证金。

9. Relayer 没被 `setOrderSender` 会怎样？

   成交不了，`INVALID_ORDER_SENDER`。

10. 这套系统和 NFTMarket 的「链上订单簿」本质差别是什么？

    NFT 的单在合约价格树里，挂单就锁进 Vault。永续的单在链下，靠 EIP-712 签名，`trade` 改的是仓位和保证金。
