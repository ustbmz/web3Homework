

## Pledge 抵押：钱先进池，凭证后发

管理员用 `createPoolInfo` 建池，`settleTime`、`endTime`、`interestRate` 在这里写死。募集期状态是 MATCH。放款人 `depositLend` 存稳定币，借款人 `depositBorrow` 存抵押物，两笔都只记 `stakeAmount`，不铸 sp、不铸 jp。

到了 `settleTime`，多签调 `settle`。抵押物按预言机价格和抵押率换成可借额，再和放款人存入额取较小的一边，写成 `settleAmountLend` 和 `settleAmountBorrow`。这一步不转币。一边供给是 0，池子变成 UNDONE，走紧急提取。

成交之后才发凭证。`claimLend` 按份额铸 sp。`claimBorrow` 铸 jp，同时把成交的稳定币打给借款人。jp 总量是 `settleAmountLend × martgageRate / 1e8`，记的是这笔债对应的抵押物份额。

到期多签调 `finish`：卖掉抵押物覆盖本金加利息。换回来的稳定币必须不少于应还额，不够就整笔回滚，状态停在 EXECUTION。`liquidate` 利息公式一样，但没有这句滑点检查，换不够的部分记在放款人账上。清算按整池，不按单个人。`liquidate` 本身只查「还在 EXECUTION、已过 settleTime」，函数里没有调用 `checkoutLiquidate`。

`withdrawLend` 要等到 FINISH 或 LIQUIDATION，拿的是 `finishAmountLend`，不是当初的 `stakeAmount`。管理员不点 `finish`，拿着 sp 也取不走本息。`validCall` 批准的是「调用者 × 这份合约」，不是某一个函数。后端 schedule 只轮询 view，不替池子发 `settle`。

## NFTMarket 订单簿：挂单就锁资产，成交才过户

卖家 `approve` 给 Vault，再 `makeOrders(List)`。`amount` 必须是 1。NFT 进金库，订单进价格树。买家 `makeOrders(Bid)` 按单价乘数量锁 ETH。`OrderKey` 是整张订单的哈希，改价等于取消旧单再挂新单。

吃单的人必须是卖单或买单的 maker。买家直接买：成交价用卖价，ETH 从 `msg.value` 出，不必事先挂 Bid。卖家接受出价：`msg.value` 必须是 0，成交价用买价，ETH 从 Vault 出。协议费留在 OrderBook，当时不打给 Owner。

`filledAmount` 写成 `uint256` 最大值表示已取消。再撮合时 `_isMatchAvailable` 过不了，错误是 `"HD: order closed"`。`matchOrders` 某一对失败只跳过这一对。Sync 扫 `LogMake`、`LogCancel`、`LogMatch` 做列表，不托管资产。

## 永续 合约：签名在链下，账在链上

用户 `deposit` 把 USDC 打进 Dealer，加的是 `primaryCredit`。这时 `Perpetual.balanceOf` 还是 0。开仓不自己调 `trade`，而是 EIP-712 签一张单，`paper` 和 `credit` 必须异号。做多 1 BTC @ 30000：`paper` 为正，`credit` 为负。

Relayer 在内存簿里配对，再以 `validOrderSender` 的身份调 `Perpetual.trade`。用户自己调会在 `approveTrade` 第一句失败，错误是 `INVALID_ORDER_SENDER`。成交价用 Maker 的 `credit / paper`。然后 `_settle` 改 `paper` 和 `reducedCredit`。`paper` 从 0 变成非 0 就记入 `openPositions`；变回 0 时，剩下的盈亏经 `realizePnl` 进 `primaryCredit`。

用户槽里只存 `paper` 和 `reducedCredit`。`credit` 不存，读的时候算：`credit = paper × fundingRate + reducedCredit`。资金费只改市场上这一个累计值，不逐个改用户。标记价变了，仓位槽不变，净值用 `markPrice` 当场算。MM 不够可以被清算，IM 不够不能开仓也不能普通取款。清算不走订单簿，任何人可调 `liquidate`，但不能清算自己。

## 撮合 现货：内存里排队，引擎不碰钱

没有合约，也没有 EIP-712。上游把委托写进这张交易对的 MySQL 表 `aibit_spot_sequence_{symbol}`。主键 `id` 就是 `SeqId`。Puller 按 `id` 从小到大拉。RabbitMQ 只把成交和行情发出去。

一个交易对一本内存簿。买单价高在前，卖单价低在前，同价 `SeqId` 小的在前。撤单用 `OrderId` 查 `cache`。成交价取 Maker。限价没吃完进自己那一侧；市价没吃完不进簿，记成撤掉。市价买的 `UnfilledAmount` 是 USDT。FOK 预扫描不够，簿上一张不动。`Stp` 默认 0，自己的买单会吃自己的卖单。

重启先装回快照，再从 `FromId + 1` 拉后面的行。编号不大于快照的挂单已经在簿里，不会再读一遍。

卖单 D 是 50001×0.8，E 是 50002×1.2。限价买 G 出 50002、要 1.5。先吃光 D，成交价 50001；再吃 E 的 0.7，成交价 50002。G 全成，不进簿。E 剩 0.5 还挂着。

## 自己写的时候，先定动钱的那一步

先写清资产在谁手里，以及哪一个函数把它转走。这个函数定下来，前面的记账、签名、订单簿都是给它准备的，列表只是把结果抄出来。

Pledge 这种，先写池子状态和 `settle`、`claimBorrow`。存款函数只记数，凭证后发。NFT 这种，先写金库和 `matchOrder`。挂单是把资产送进 Vault，成交才过户。永续这种，先写 `paper`、`credit` 和 `trade`。用户用签名授权，Relayer 的簿可以后接。现货撮合这种，先写内存订单簿和 `SeqId`。引擎只产出成交结果，余额留在上游账户。

这个函数有了，再写谁能调用、挂了状态留在哪。多签推进、白名单提交、序列加快照，都是为了这一步能重放、能对上账。接口和列表放在最后。
